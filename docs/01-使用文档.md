# XR 遥操作服务 — 使用文档

> 适用版本：本地定制分支 `integration/upstream-v1.6`（已合入上游 v1.6）
> 适用机型：Unitree G1_29 / G1_23 / H1_2 / H1 / H2 / R1_A5 / R1_A7
> 文档日期：2026-10-30

---

## 1. 这个系统是做什么的

一句话：**让操作者戴上 XR 头显（Pico / Quest / Apple Vision Pro），用手和身体的动作实时驱动一台人形机器人的手臂和手**，同时把机器人头部双目相机的画面推回头显里，形成"我在机器人身体里"的沉浸视角。

它属于 `autobot-guide-service` 体系中的**机器人端**组件。Web 控制台通过它拿到遥操画面与相机图像流；它本身不做业务编排，只负责"动作采集 → IK 解算 → 关节指令下发"这条实时链路。

**它不是**：不是自主导航，不是强化学习训练框架，也不是远程运维平台。它是一条对延迟极敏感（30–250 Hz）的实时控制通道。

## 2. 能力矩阵

### 2.1 支持的机器人（`--arm`）

| 取值 | 机型 | 说明 |
|---|---|---|
| `G1_29` | Unitree G1（29 自由度身体 + 14 自由度手） | **默认值**，现场主力机型 |
| `G1_23` | Unitree G1（23 自由度） | |
| `H1_2` | Unitree H1_2 | |
| `H1` | Unitree H1 | 仅仿真模式 |
| `H2` | Unitree H2 人形 | v1.6 新增 |
| `R1_A5` | Unitree R1（5 自由度手臂） | v1.6 新增 |
| `R1_A7` | Unitree R1（7 自由度手臂） | v1.6 新增 |

每个机型在 `assets/<机型>/` 下有独立的 URDF 与网格，IK 解算使用 Pinocchio 加载对应模型（首次加载较慢，之后走 `g1_29_model_cache.pkl` 缓存）。

### 2.2 支持的末端执行器（`--ee`）

| 取值 | 末端 | 备注 |
|---|---|---|
| `dex1` | Unitree Dex1-1 二指夹爪 | 需配套 `third_party/dex1_1_service` 服务 |
| `dex1_internal` | Dex1 内部夹爪服务 | **仅 G1_29**，且**不支持 `--motion`** |
| `dex3` | Unitree Dex3-1 灵巧手 | 不支持手柄输入模式 |
| `inspire_ftp` / `inspire_dfx` | 因时 Inspire 灵巧手（两种协议） | 不支持手柄输入模式 |
| `brainco` | 强脑 BrainCo 灵巧手 | 支持手势 + 手柄两种输入 |

不传 `--ee` 时为**纯手臂遥操**（无末端动作）。

### 2.2.1 末端是自动识别的

启动脚本会订阅 DDS 状态话题，判断机器人上实际装着哪种末端（Dex3 / Inspire / BrainCo / Dex1），
并把结果作为默认选项；现场只需回车确认。判断依据见《操作文档》第 3.1 节。

### 2.3 输入与显示模式

| 参数 | 取值 | 含义 |
|---|---|---|
| `--input-mode` | `hand` | 手势跟踪（裸手，靠手部关键点） |
| | `controller` | 手柄跟踪（握持手柄，用扳机/摇杆） |
| `--display-mode` | `immersive` | 沉浸模式，头显里显示机器人相机画面（默认） |
| | `ego` | 第一人称混合视角 |
| | `pass-through` | 透视，直接用头显自己的摄像头 |

## 3. 系统组成

```
        ┌──────────────┐   动作/按键    ┌────────────────────────┐
        │  XR 头显      │ ────────────► │ televuer (8012, HTTPS) │
        │ Pico/Quest/AVP│ ◄──────────── │ 动作采集 + 画面回传     │
        └──────────────┘   相机画面     └───────────┬────────────┘
                                                    │ 腕部/手部目标位姿
                                                    ▼
        ┌──────────────┐    图像帧     ┌────────────────────────┐
        │ teleimager   │ ────────────► │ teleop_hand_and_arm.py │
        │ (60001 WebRTC│               │  主控循环 30 Hz         │
        │  + /status)  │               └───────────┬────────────┘
        └──────┬───────┘                           │ 关节角 + 力矩
               │ 取流                              ▼
        ┌──────┴───────┐               ┌────────────────────────┐
        │ 头部双目相机  │               │ robot_arm.py / _ik.py  │
        │ SCAM/RealSense│              │ Pinocchio IK + 限幅     │
        └──────────────┘               └───────────┬────────────┘
                                                   │ DDS (eth0)
                                                   ▼
                                       ┌────────────────────────┐
                                       │ 机器人运控 (G1/H2/R1)   │
                                       └────────────────────────┘
```

### 3.1 组件职责

| 组件 | 路径 | 职责 |
|---|---|---|
| 主控程序 | `teleop/teleop_hand_and_arm.py` | 参数解析、DDS 初始化、启动各控制器与线程、主循环 |
| 手臂控制 | `teleop/robot_control/robot_arm.py` | 8 个机型的 `*_ArmController`，DDS 收发 + 速度/加速度限幅 |
| IK 解算 | `teleop/robot_control/robot_arm_ik.py` | 7 个机型的 `*_ArmIK`，CasADi + Pinocchio 求逆解 + 出口安全闸门 |
| 手部驱动 | `robot_hand_unitree.py` / `robot_hand_inspire.py` / `robot_hand_brainco.py` | Dex1 / Dex3 / Inspire / BrainCo |
| 机器人 FSM | `teleop/robot_control/robot_fsm.py` | G1 运动控制状态机（本地新增） |
| 图像服务 | `teleop/teleimager/` | 相机采集 + WebRTC/ZMQ 分发 + `/status` 机器人状态 |
| XR 交互 | `teleop/televuer/` | Vuer WebXR 服务、动作解算、画面渲染、静态看板 |
| 夹爪服务 | `third_party/dex1_1_service/` | C++ 串口→DDS 桥（预编译 aarch64） |
| 相机启动脚本 | `scripts/start_camera.sh` | 自动探测双目 → 深度 → 无相机，按结果选配置并拉起图像服务 |
| 遥操启动脚本 | `scripts/start_teleop.sh` | 选末端（无手/两指/三指/因时）→ 夹爪体检 → 拉起主程序；兼做远程启停 |
| 心跳上报 | `scripts/heartbeat_register.py` | 每 30 s 把本机地址推给后端 |

## 4. 网络与端口

### 4.1 网络拓扑（以 192.168.2.203 这台为例）

| 网卡 | 地址 | 用途 |
|---|---|---|
| `eth0` | `192.168.123.164` | **DDS 通道**（机器人内部网），`--network-interface eth0` |
| `wlan0` | `192.168.2.203` | **XR / WebRTC 通道**，头显与操作电脑接入这个网 |
| `docker0` | `172.17.0.1` | Docker 网桥，遥操本身不用 |

关键点：**DDS 和图像走的是两张网卡**。启动脚本用 `detect_robot_ip wlan0` 取 `192.168.2.203` 作为 `--img-server-ip`，而 DDS 固定走 `eth0`。把这两者搞混是现场最常见的连不上原因。

### 4.2 端口清单

| 端口 | 服务 | 协议 | 说明 |
|---|---|---|---|
| 60000 | teleimager | TCP | 相机配置查询（ZMQ REP） |
| **60001** | teleimager | **HTTPS/WHEP** | 头部双目画面 + `/status` + `/health` |
| 60002 / 60003 | teleimager | HTTPS | 左/右腕相机（默认未启用） |
| 55555 / 55556 / 55557 | teleimager | ZMQ | 头/左腕/右腕图像帧（默认 `enable_zmq: false`） |
| **8012** | televuer | **HTTPS/WSS** | XR 头显打开的页面：`https://<wlan0-ip>:8012` |

> 历史端口 `8013`（独立 robot-agent 状态服务）已合并进 `60001`，前端 `/status` 字段保持不变，不再需要单独端口与证书。

## 6. 相机配置

配置文件：`teleop/teleimager/cam_config_server.yaml`

### 6.1 关键字段（头部相机）

| 字段 | 当前值 | 说明 |
|---|---|---|
| `type` | `scam` | 相机后端，可选 `opencv` / `realsense` / `scam` |
| `enable_webrtc` | `true` | 头显画面走 WebRTC |
| `enable_zmq` | `false` | 录制取图走 ZMQ，**关掉就没有图像帧可录** |
| `webrtc_port` | `60001` | |
| `binocular` | `true` | 双目 |
| `stereo_sbs` | `true` | 左右并排（SBS）单流 |
| `stereo_split_webrtc` | `false` | `true` 时左右眼分两个端口（60001/60002） |
| `image_shape` | `[720, 2560]` | 送显分辨率 |
| `capture_image_shape` | `[1200, 3840]` | 采集原始分辨率（单眼 1920×1200） |
| `fps` | `30` | |
| `video_id` | `6` | SCAM 枚举出的 `/dev/videoN`（弱信号） |
| `physical_path` | `null` | **权威定位**，填 sysfs 相机接口路径 |

### 6.2 `physical_path` 的坑（务必注意）

必须填**相机接口**路径（该目录下有 `video4linux/videoN` 子目录），**不要**填 USB Hub 的接口路径。

原因：Hub 的 sysfs 路径永远存在，会导致"相机在位"判断恒为真 → 永远不会回退到 RealSense → 按 SCAM 启动后反复崩溃。这是 2026-09-28 的线上故障根因，已在代码中修复（要求路径含 `video4linux/` 或 `bInterfaceClass=0e`，并排除 RealSense 的 USB VID `8086`）。

查真实路径：

```bash
bash scripts/start_camera.sh --find-camera
```

### 6.3 IMU 电子防抖（EIS）

`stabilization.enabled: true`，靠头部相机 IMU 做陀螺仪防抖。当前 `use_eskf: false`（加计方向未标定，ESKF 量测会抵消零偏修正），用 `ImuAttitude + relearn_beta` 替代。

> `axis_sign: [-1.0, -1.0, 1.0]` 尚待旋转验证（代码注释标注"重力实测建议 IMU 相对相机 180° roll"）。若发现画面防抖方向反了，先查这里。

## 7. 安全机制

这套代码在"人会动、机器人会伤人"的前提下做了多层限幅。**改这些值之前请确认你在做什么。**

### 7.1 手臂速度与加速度

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `XR_ARM_VELOCITY_LIMIT_START` | `1.5` rad/s | 启动时速度上限 |
| `XR_ARM_VELOCITY_LIMIT_MAX` | `3.0` rad/s | 渐变到顶后的速度上限 |
| `XR_ARM_VELOCITY_LIMIT_SIM` | `30.0` rad/s | 仿真模式上限 |
| `XR_ARM_ACCEL_LIMIT` | `10.0` rad/s² | 加速度上限，避免指令阶跃 |
| `XR_ARM_TRACKING_ERROR_LIMIT` | `0.15` rad | G1_29 指令与实测位置的最大偏差 |
| `XR_ARM_LOWSTATE_TIMEOUT` | `0.5` s | lowstate 超时判陈旧 |

> 设计说明：上游原实现把 20 → 30 rad/s 当"限速"。G1 臂展约 0.7 m，20 rad/s 换算到末端接近 14 m/s，这已经不能提供任何保护。本地按"人臂快速摆动"量级收窄到 1.5 → 3.0 rad/s。
>
> 主程序启动时调用 `speed_gradual_max()`，在 5 秒内从 START 线性升到 MAX，避免一开始就满速。

G1_29 从上一条成功下发的指令推进连续轨迹，独立限制速度、加速度和跟踪误差。DDS 状态过期时冻结最后成功下发的位置与前馈力矩。修复与验证详情见《手臂跟随修复》。

### 7.2 IK 出口硬闸门

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `XR_IK_STEP_MAX` | `0.1` rad/周期 | 单周期最大关节步长（30 Hz 下 = 3.0 rad/s，**必须与 `XR_ARM_VELOCITY_LIMIT_MAX` 对齐**） |

处理顺序：**有限性检查 → 关节限位 clamp → 单周期步长截断 → 再进滑动平均滤波**。

G1_29 的步长以之前有效的 IK 解为基准，热启动使用上一帧滤波结果；XR 输入无效或求解失败时清除历史窗口和参考解。正常跟踪误差由发布器单独约束。

为什么顺序不能反：滑动平均只是平滑，不是限幅。一次 2~3 rad 的跳变会被分摊到 4 个周期，30 Hz 下仍相当于 20+ rad/s。必须在滤波之前截断。

> ⚠️ **两个限幅层必须对齐**。IK 闸门（`XR_IK_STEP_MAX`）在 `robot_arm.py` 的速度限幅
> （`XR_ARM_VELOCITY_LIMIT_MAX`）之前执行，谁更小谁就是实际速度上限。
> 曾经 IK 闸门设 0.05（=1.5 rad/s）而速度上限设 3.0，结果手臂只跟到一半，
> 调速度上限完全无效。改速度前请两个一起看。

求解失败时**保持当前实测位置**，且不把失败迭代点写进 `init_data`（否则下一帧从坏点热启动，可能连续失败）。

### 7.3 就绪门控

- `xr_motion_data_ready`：XR 动作数据没到之前，不下发末端指令
- 夹爪额外要求"首帧非零输入"：收到第一个非零值才认为 VR 数据就绪；之后即使输入精确为 `0.0`（扳机按到底）也继续映射，否则夹爪会停在最后位置无法完全闭合
- `XR_HAND_READY_TIMEOUT`（默认 `10` 秒）：DDS 订阅超时，避免初始化无限阻塞

## 9. 与 autobot-guide-service 的集成

`card-module.json` 是部署契约：

| 字段 | 值 |
|---|---|
| `defaultDirectory` | `/home/unitree/xr_teleoperate/` |
| `arch` | `arm64` |
| `entrypoint.command` | `./scripts/start_teleop.sh` |
| `service.name` | `xr-teleimager`（服务开关与开机自启目标） |
| `manualStartScripts` | `scripts/start_teleop.sh` |
| `healthCheck` | 进程匹配 `teleimager`，60 s 超时 |

**设计上刻意不做的事**：遥操主程序**不注册为 systemd 常驻服务**、不 enable、不设开机自启。它一启动就会接管机器人手臂，必须由现场人员手动执行。部署器侧还有 unit 名黑名单 + ExecStart 检查作为兜底。
